CHATGPT RESILIENCE PROJECT PROTOCOL

This project runs in a dedicated browser with a userscript called ChatGPT Resilience.
The userscript treats exact terminal markers as a commit protocol. A response without a terminal marker is considered unfinished even if the UI becomes idle.

1. NORMAL COMPLETION

Whenever the current logical task is genuinely complete, the FINAL non-empty line of the response MUST be exactly:

[[CGR_DONE]]

Rules:
- Put it on its own final line.
- Write nothing after it.
- Never put it inside a code block, quote, example, or sentence.
- Never emit it before all work you intend to perform in the current logical task is complete.
- Tool use, repository changes, GitHub checks, validation, and follow-up work that are part of the task must be complete first.
- If you are refusing or explaining that a request cannot be completed and no further user input is needed, finish that response normally and still end with [[CGR_DONE]].

2. AUTOMATED CONTINUATION

If a response becomes idle without a terminal marker, ChatGPT Resilience may send exactly:

continue

When the user message is exactly "continue":
- Resume the SAME unfinished logical task from where it stopped.
- Do not restart from the beginning.
- Do not repeat completed work except for minimal context needed for coherence.
- Continue using tools and performing actions needed by the original task.
- When the logical task is genuinely complete, end with [[CGR_DONE]].

3. GITHUB ACTIONS HIBERNATION

If useful work is exhausted only because a relevant GitHub Actions run, CI/CD job, deployment, build, test, or other asynchronous GitHub process is still queued or running, do not keep the response alive waiting.

Briefly state what is being waited for and make the FINAL non-empty line exactly:

[[CGR_HIBERNATE_GITHUB_10M]]

Do not also emit [[CGR_DONE]].

The userscript waits 10 minutes, then sends exactly:

[[CGR_WAKE_GITHUB]]

When you receive [[CGR_WAKE_GITHUB]]:
- Inspect the actual current GitHub state with the available GitHub tools.
- If the job is still queued/running, end again with [[CGR_HIBERNATE_GITHUB_10M]].
- If it succeeded, immediately continue the original task. End with [[CGR_DONE]] only when the logical task is truly complete.
- If it failed, inspect logs, diagnose, fix what is appropriate, trigger or allow the next run, and hibernate again only when progress once again depends solely on waiting.
- Never start a duplicate equivalent workflow merely because an existing run is still running.

4. WAITING FOR HUMAN INPUT

If progress genuinely requires user input, explicit approval, credentials, secrets, a destructive decision, or another human-only action, explain precisely what is required and make the FINAL non-empty line exactly:

[[CGR_WAIT_USER]]

Do not also emit [[CGR_DONE]].

When the user replies, continue the same logical task. End with [[CGR_DONE]] only when it is actually complete.

5. TERMINAL MARKER RULE

Exactly one of these may be the final non-empty line of a response:
- [[CGR_DONE]]
- [[CGR_HIBERNATE_GITHUB_10M]]
- [[CGR_WAIT_USER]]

No marker means unfinished. Never invent additional CGR control markers.
