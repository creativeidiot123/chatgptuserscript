ChatGPT Resilience v1.3.27 — wiring / edge-case audit

Core contract
-------------
- Runtime state is browser-tab local via sessionStorage.
- Queue contains FUTURE text-only messages.
- Transaction journal contains ACTIVE logical work.
- Queueing is always enabled. There is no queue pause/resume state.
- Normal Enter / native Send:
    generating -> queue
    idle       -> native send
- Queued messages have exactly one dispatch path: the automatic queue pump.
- The pump is locked unless the CURRENT rendered assistant tail ends in
  [[CGR_DONE]].
- Errors, [[CGR_HIBERNATE_GITHUB_10M]], [[CGR_WAIT_USER]], recovery, generation,
  and ambiguous states never release queued work.
- There is no manual queued Send/Steer bypass.

Queue release readiness
-----------------------
A queued item may dispatch only when ONE canonical gate reports no block:
- current assistant tail ends in [[CGR_DONE]]
- no recognized error
- no active/pending recovery or control fault
- no hibernation state (sleeping, waking, or wait-user)
- no active transaction
- not generating
- no verifier
- not paused or blocked
- no action in flight or send intent
- browser is online

Unresolved long-thinking is represented by recovery/pending-recovery state, so it
must finish its Stop -> wait -> continue flow before the queue can release.
If [[CGR_DONE]] is later committed, that protocol result is the proof that the
recovered logical task has actually finished.

The gate is checked twice: before queue staging and again after durable state +
live DOM are refreshed, closing races with newly-started recovery/hibernation.

Queue dispatch
--------------
1. The current assistant tail must end in [[CGR_DONE]].
2. Every other state leaves the queue inert.
3. Programmatic dispatch reserves actionInFlight.
4. Queue mutations are frozen during the short dispatch window.
5. The transaction journal is persisted before a queued item is removed.
6. queueItemId is only a transient crash-recovery claim.
7. Queue removal is persisted before the claim pointer is cleared.
8. Native Send is clicked only after the durable transaction/queue handoff.
9. Once one queued item sends, its new user turn closes the DONE gate again.
10. If the click is swallowed or the tab dies, the journal owns recovery; the
    future queue item is not duplicated.

Healthy-answer continue audit
-----------------------------
Automatic literal "continue" can only originate from stopThenContinue(). The deep
audit found these prior false-positive sources and closes each one:

1. Composer Send/Voice transitions
   - Formerly could trigger a 350 ms control-mismatch Stop.
   - Removed in v1.3.24.

2. Long-thinking banner
   - Formerly requested recovery immediately.
   - Now requires 10 continuous minutes before recovery is eligible.
   - Ordinary prose containing "still thinking" no longer qualifies.

3. Fetch/XHR aborts
   - Formerly became recoverable network failures.
   - Abort is now treated as ordinary cancellation noise.

4. Broad/stale network ownership
   - Conversation-like POST failures could belong to background or older work.
   - Recovery network evidence is now accepted only for a request that started
     within 15 seconds of the active dispatch and still matches route, logical
     transaction, subturn dispatch timestamp, and current prompt hash.

5. Previous-turn Retry/Regenerate UI
   - A previous assistant turn could briefly remain DC.lastAssistant after the
     next user turn appeared.
   - Retry evidence now requires the real current assistant tail / current
     user-to-composer corridor.
   - Regenerate is normal answer UI and is never failure evidence.

6. Assistant prose false positives
   - Long/old assistant text ending in error-like wording could look like product
     error chrome.
   - Only the current assistant tail is considered, and prose-tail classification
     is limited to compact product-error-sized messages.

7. Composer remount
   - A normal React composer disappearance/remount could manufacture
     composer-missing / composer-remounted recovery.
   - Composer lifecycle alone can no longer create a recovery reason; it only
     defers independently proven recovery.

8. Stale cross-turn state
   - Long-thinking age and transient HTTP/network evidence could leak into the
     next subturn.
   - New sends/tasks reset those transient recovery signals.

9. Error semantics
   - Rate limits could fall through the generic continue path.
   - Hard errors now block, rate limits pause, confirmed send errors are ignored,
     and only recoverable errors may request continuation.

Final destructive-recovery boundary:
- Ordinary error/UI/network recovery cannot click Stop while independent live
  generation evidence exists.
- Even forced stuck recovery requires at least 15 seconds without fresh assistant
  tail progress.
- The only callers allowed to bypass the live-control veto are:
    * 10-minute long-thinking timeout
    * 15-minute tracked stuck timeout
    * 15-minute untracked stuck timeout
- Terminal DONE / HIBERNATE / WAIT_USER markers still hard-veto continuation.

Generation detection
--------------------
Composer controls are signals, not a single source of truth.

Strong independent busy evidence:
- visible Stop control
- composer spinner / streaming state
- assistant streaming attributes
- recent assistant DOM progress during the settle window
- active long-thinking banner

Typing a human follow-up or ChatGPT's own UI transitions can temporarily expose
Send/Voice while generation continues. Therefore:
- Send + draft never proves generation ended.
- Independent busy evidence and recent assistant DOM progress beat transient
  Send/Voice affordances.
- If the evaluator already says generating, a human draft cannot demote it.
- Send/Voice alone never trigger Stop -> continue recovery.
- Idle-without-marker is handled by the five-minute quiet verifier instead.
- There is no draft timeout that can expire into a false idle state.
- Generation evidence is reset on project-chat route changes and runtime exit.

Human overrides / hibernation
-----------------------------
- Native human sends remain separate from queued-message dispatch.
- Queued messages never override sleeping, waking, wait-user, or errors.
- Waking state remains serialized by actionInFlight.
- Automatic queue advancement stays blocked until a later [[CGR_DONE]].

Queue editing
-------------
- Queue-edit text is isolated from normal composer draft persistence.
- Starting an edit clears any stale normal draft.
- Edit keystrokes are not persisted as a separate draft.
- Escape really cancels the edit and clears the composer.
- Route changes cannot resurrect queue-edit text as an ordinary draft.

Input edge cases
----------------
- Human typing can replace ChatGPT's Stop control with the user's Send control.
  While a draft exists, that UI change is NEVER allowed to demote an already
  active generation.
- Enter, native Send click, and form submit share one fail-safe guard. If the
  evaluator already says generating, the input path must queue.
- If the script says generating, intercepted Enter/Send/submit always queues the
  text and leaves it queued. It never performs a speculative post-clear auto-send.
- If the busy message contains attachments, native sending is blocked and the
  user is asked to wait because attachments cannot be reconstructed safely.
- Ambiguous state therefore fails safe toward queueing/blocking instead of
  risking interruption of a live answer.
- Held/repeated Enter is swallowed so repeated keydown events cannot bypass the
  queue interceptor.
- Shift+Enter remains available for multiline input.
- Attachments are deliberately not queued because they cannot be reconstructed
  safely.
- Native Send and Enter share the same generating-vs-idle queue rule.
- Ctrl+Enter remains an explicit immediate send/steer path.

Race / mutation safety
-----------------------
During actionInFlight:
- add-from-composer, delete, clear, reorder, begin-edit, and commit-edit queue
  mutations all fail closed;
- queue controls are rendered disabled;
- a reorder/delete cannot race a staged prompt and change which item is sent.

PASS  active generation + human draft + hidden Stop -> remains generating
PASS  hidden-Stop draft preserves active generation until the draft clears
PASS  idle + draft -> stays idle
PASS  empty Send without busy evidence -> idle
PASS  Voice without busy evidence -> idle
PASS  busy evidence beats transient empty Send
PASS  busy evidence beats transient Voice
PASS  composer control changes alone cannot trigger Stop
PASS  live assistant progress defers automatic Stop recovery
PASS  fetch/XHR abort noise is not treated as a recovery failure
PASS  ordinary "still thinking" prose does not trigger long-thinking recovery
PASS  Regenerate is not retry/error evidence

SPA project activation
----------------------
- Tampermonkey injects the userscript on https://chatgpt.com/*, not only /g/*.
- Runtime behavior remains hard-gated by isProjectUrl() to /g/... routes.
- Opening ChatGPT at / or /c/... therefore loads only the dormant shell.
- The always-installed history/popstate route hooks detect SPA navigation into
  /g/... and activate the project runtime without requiring a page refresh.
- SPA navigation back out of /g/... deactivates observers/UI/runtime state.
- Input/network/recovery handlers continue to fail closed outside project routes.

Hard terminal veto
------------------
- Exact visible protocol tokens are authoritative even if the surrounding
  assistant container has extra suffix text. The rendered token is not discarded
  just because flattened text has trailing UI/content.
- Literal recovery "continue" checks for a fresh terminal marker before staging.
- Recovery continue also requests a final forced marker check inside dispatchPrompt
  after all awaits and immediately before synchronous journaling + native Send.
- There is no await between that final veto and the click, so React/network DOM
  updates cannot interleave and sneak a terminal marker into the send window.
- If the final veto fires, the staged "continue" is cleared and the evaluator is
  re-run to commit DONE / HIBERNATE / WAIT_USER normally.

Terminal-marker preemption
--------------------------
- A valid current-subturn [[CGR_DONE]], [[CGR_HIBERNATE_GITHUB_10M]], or
  [[CGR_WAIT_USER]] immediately preempts every recovery path.
- The short assistant-tail settle delay is only for durable marker commit. It is
  never a window in which Stop/10s/continue may run.
- Any already-active recovery is cancelled through the single existing
  cancelRecovery() path. A sleeping 10-second recovery then fails its ownership
  check and exits without sending literal "continue".
- This prevents hibernate/wait-user/done markers from racing with long-thinking,
  error, verifier, or stuck-turn recovery.

Mid-generation Stop protection
------------------------------
- Composer Send/Voice state is not a recovery trigger.
- The old 350 ms control-mismatch Stop path was removed completely.
- Healthy generation stays active when assistant DOM progress or streaming/busy
  evidence is still present, even if the composer transiently shows Send/Voice.
- Even explicit recoverable signals cannot click Stop until assistant-tail
  progress has been quiet for 15 seconds.
- Missing terminal markers are recovered only through explicit error handling,
  the long-thinking path, or the five-minute quiet verifier.

Recovery boundary
-----------------
- No automatic recovery may click Stop while the current assistant turn is still
  visibly progressing.
- Recoverable error, transport, long-thinking-timeout, verifier, and pending
  recovery signals all funnel through stopThenContinue().
- Ordinary recovery cannot Stop while live generation evidence exists.
- Only the explicit 10-minute long-thinking and 15-minute stuck paths may bypass
  the live-control veto, and even those still require 15 seconds without fresh
  assistant-tail progress.
- The five-minute stuck verifier naturally satisfies this guard.
- Fetch/XHR aborts are ignored as normal request cancellation noise rather than
  being promoted to recoverable network errors.

Long-thinking recovery
----------------------
- Known ChatGPT "thinking a bit more" product text starts a timer; it does not
  request destructive recovery until it has remained visible for 10 minutes.
- Generic prose containing "still thinking" is not enough. Only the known product
  phrases or an element whose whole text is essentially "Still thinking..." count.
- If the transaction journal is missing, the current visible user/assistant tail
  is adopted immediately instead of waiting for the generic five-minute orphan
  timeout.
- If the journal exists but its user-turn confirmation was lost, the visible
  current turn is reconciled before recovery.
- Recovery remains: click Stop -> wait until the composer shows a settled
  Send/Voice/idle state -> wait 10 seconds -> send literal "continue".
- The long-thinking banner may remain mounted after Stop, so post-Stop settling
  intentionally ignores that banner and trusts the actual composer controls.

Notifications
-------------
- [[CGR_WAIT_USER]] sends a desktop notification when the runtime transitions
  into wait-user.
- Repeated evaluation/reload passes do not re-notify while the persisted
  wait-user state is already active.
- [[CGR_DONE]] sends a desktop notification only after the transaction has been
  durably completed.
- Every successfully dispatched literal "continue" sends a desktop notification
  with its exact internal reason and continuation count, for example:
    ChatGPT Resilience: continue #3/16
    Reason: error:network
  This includes automatic recovery and explicit manual/menu/console continue
  actions because all of them share sendLiteralContinue().
- A notification is emitted only after dispatchPrompt() succeeds, so blocked,
  vetoed, or failed continuation attempts do not produce false diagnostics.
- [[CGR_HIBERNATE_GITHUB_10M]] does not notify.

Blind stuck timeout
-------------------
- The generic unfinished-turn timeout is now 15 minutes instead of 5 minutes.
- This applies consistently to tracked stuck generation, idle missing-marker
  verification, and untracked orphan-turn adoption.
- Diagnostic reasons were renamed to stuck-15m / untracked-stuck-15m so continue
  notifications identify the new timeout clearly.
- The unrelated two-reloads-per-5-minutes safety window is unchanged.

Continuation safety
-------------------
- A logical task may auto-send literal "continue" up to 16 times.
- A 17th required continuation trips continue-safety-cap, preserves the queue,
  and requires manual attention.
- GitHub hibernation cycles do not consume this counter. Sleeping, waiting, and
  the WAKE prompt are separate from literal recovery "continue" turns.

Known intentional behavior
--------------------------
- Queue progression happens only after [[CGR_DONE]] on the current assistant tail.
- A single DONE can release at most one queued item because that send creates the
  next user turn and closes the gate again.
- Hibernate, wait-user, errors, recovery, and unfinished tails never release it.
- Recovery/rate-limit pauses are separate from the removed queue pause feature.
- Existing bounded page-reload recovery remains part of the recovery subsystem;
  it is not part of queue dispatch.
